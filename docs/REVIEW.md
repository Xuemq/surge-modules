# 候选模块审查清单

这份清单用于审查本工具的来源输入、转换与合并结果。它不构成已经完成审查的证明。每次更新都应保留实际日期、输入 SHA-256、工具版本、审查人以及结果；不要把未执行的检查勾选为通过。

## 1. 核对输入

- [ ] 对照 `sources.json` 确认来源身份、完整 URL、格式与预期用途。
- [ ] 确认本次获取的是清单中指定的文件，没有擅自更换镜像或同名仓库。
- [ ] 比较实际 SHA-256 与锁定值，记录新增、变化、不可下载和缺失的来源。
- [ ] 检查异常重定向、HTML 错误页、截断下载或无法解码的内容，不把它们当作规则文件。
- [ ] 对变化逐项复核后再修改锁定元数据，不通过自动“接受最新哈希”消除告警。
- [ ] 不加载、不执行来源正文中的命令或 JavaScript，不递归下载未列入清单的依赖。

`check-updates` 的职责是报告状态，不是自动接受更新。网络失败也不能证明上游没有变化。

## 2. 清理许可阻断

当前来源审查仍待完成：存在 GPL-2.0、GPL-3.0 许可线索，以及未找到明确许可的输入。不能仅凭仓库首页名称判断具体文件受何种许可覆盖，也不能把许可证标识的数字视为可自由组合的依据。

每个来源分别记录：

- [ ] 对应文件及其来源版本；许可证的官方位置和审查日期。
- [ ] 许可证是否明确覆盖该文件，版本和可选版本条款是否清楚。
- [ ] 文件头、仓库说明和独立版权声明是否一致；有无额外归属或第三方来源。
- [ ] 复制、修改、转换和公开再分发分别需要履行什么条件。
- [ ] 是否需要保留版权通知、许可全文、来源说明和修改记录。
- [ ] 合并结果的许可与每个输入是否相容；不确定时继续阻断并向权利人核实。
- [ ] 来源引用的脚本、资源和其他依赖是否具有独立授权要求。

无明确许可的来源继续保留“待确认”状态，不能把“作者公开发布了文件”改写为“允许本仓库再分发”。未清理前，公开仓库仅保存本项目原创实现、测试、文档及审查元数据，不保存上游正文或生成模块。

许可通过只解决发布前置条件中的一项；它不会使未通过兼容性检查的模块变得可用。

## 3. 检查 QX 转换

- [ ] 查看转换报告中的每一个不支持、未知或需要人工确认的条目。
- [ ] 确认不存在因忽略未知语法而静默减少功能的情况。
- [ ] 逐项核对受支持操作在 QX 与 Surge 中的语义、请求／响应方向及作用范围。
- [ ] 核对脚本的触发类型、正文读取需求、二进制处理、超时和运行时 API。
- [ ] 单独审查远程脚本。只转换声明，不能证明脚本正文能够在 Surge 运行。
- [ ] 检查转换失败后是否仍留有旧输出；以本次退出码和报告为准，不拿旧文件当作新结果。

转换器采取失败关闭策略。遇到无法安全表示的指令、未知语法或未经确认的脚本兼容性时，应停止本次候选生成。对实际输入出现未解决条目是正常审查结果，不应伪装成“完整转换成功”。

Surge 的脚本定义和执行环境见 [Scripting 官方说明](https://manual.nssurge.com/scripting/overview.html)。

## 4. 审查合并与冲突

- [ ] 检查重复项是否只是完全相同的文本，还是相同作用目标配上了不同操作。
- [ ] 每个冲突均有明确来源、处理决定及理由；没有未解决的冲突被顺序悄悄覆盖。
- [ ] 不使用简单字母排序重新安排有先后语义的规则。
- [ ] 检查相同脚本名称、相同匹配文本、不同请求／响应阶段以及跨节相互影响。
- [ ] 核对 MITM 主机追加与排除顺序，避免无意扩大解密范围。
- [ ] 核对模块元信息、必要的版本限制和目标平台。
- [ ] 对比上一份人工确认版本，记录新增、删除、变更及行为风险。

工具仅实现有限的静态冲突检查，不检查任意正则的等价性，也不能证明不同正则没有交集。手工确认仍须关注同一请求被多个规则命中的情况。模块与主配置的覆盖和插入方式见 [Module 官方说明](https://manual.nssurge.com/profile/module.html)。

## 5. 检查 Surge iOS 运行条件

本次审查的 fmz 文件包含 Body Rewrite 和 jq 功能。官方最低版本分别为 Surge iOS 5.10.0 和 5.14.0；不能据此推断所有内容只需要这些版本，应继续核对最终文件用到的功能与实际安装版本。[Body Rewrite 官方说明](https://manual.nssurge.com/http/body-rewrite.html)

- [ ] 记录实际测试的 Surge iOS 版本、系统版本和候选文件 SHA-256。
- [ ] 保存可恢复的原有配置，先在可控的测试环境中手动验证候选。
- [ ] 确认模块解析、启用与日志无异常；分别测试命中和不应命中的请求。
- [ ] 对脚本、Body Rewrite、jq 和相关主机覆盖情况分别记录结果。
- [ ] 验证有冲突风险的规则顺序，以及与其他启用模块的组合行为。
- [ ] 检查应用基本功能、登录、加载和必要请求未被误伤。
- [ ] 确认 HTTPS 改写的必要 MITM 条件；不要为测试而提交 CA、私钥、口令或完整个人配置。
- [ ] 测试禁用候选后的恢复行为。

这些设备测试**尚未由本仓库的 CI 执行**。CI 运行的是 Python 测试与元数据检查，不是 Surge iOS。MITM 的作用范围和风险参考 [官方说明](https://manual.nssurge.com/http/mitm.html)。

## 6. 保持候选与发布分离

- [ ] 哈希、输入完整性、不支持的转换以及未解决的冲突均已通过构建检查。
- [ ] 本次构建成功，输出确为本地 `work/` 目录中的新候选，并记录其哈希。
- [ ] 许可与再分发审查另行通过；没有因为本地构建成功就开放发布。
- [ ] 已取得发布当前内容与目标的明确授权，且人工验证记录可追溯。
- [ ] 检查 Git 暂存区，确保没有个人主配置、凭据、证书、缓存、下载原文或未获准的生成文件。
- [ ] 在允许再分发之后，另行设计并审查稳定版本、变更日志、回滚和订阅地址；本工具不自动提升稳定版本。

`.gitignore` 不能阻止强制添加，也不能隐藏已被追踪的文件。任何发布前都应主动检查暂存内容。当前仓库不提供稳定模块订阅 URL，不应向设备分发未经审查的候选。

## 7. 读取 Actions 结果

`ci.yml` 提供只读权限的提交、PR 和手动单元测试。每日更新检查、草稿 PR 与发布工作流尚未实现。check-updates 可在本地运行，其更新报告只含有限元数据，不包含原始规则或脚本正文。

下列情况均不能被当作成功：

- 下载失败、来源缺失，或报告缺失／格式错误。
- 哈希与锁定值不同，且尚未人工接受。
- 报告中的冲突、转换或许可门禁仍阻断。
- 测试失败，或更新检查返回非零退出码。

当前许可未清理时，预期会看到阻断。修正事实和补齐审查证据后再调整元数据，不通过删除失败步骤、忽略退出码或放宽权限解决。

## 8. 可选的未来草稿 PR 流程

当前未实现自动 PR。若仓库所有者后续决定启用，应先确认：

1. 仓库允许 GitHub Actions 创建 PR 的设置由所有者明确开启。
2. 工作流的 `contents: write` 与 `pull-requests: write` 权限经单独批准，只覆盖需要写入的作业。
3. 提交范围只含经过审查的允许内容；许可未清理时仍不可提交上游正文、生成模块或正文片段。
4. 变化只产生待人工审阅的草稿 PR，不自动合并，不自动发布，不提升稳定版本。
5. PR 显示来源哈希变化、阻断项和人工验证状态，并保留现有版本。

本说明不是启用这些设置或授予写权限的授权。当前工作流保持 `contents: read`，不会静默升级。
